# Client-Usable SWIFT Platform Implementation Report

Date: 2026-08-05  
Plan: [CLIENT_USABLE_SWIFT_PLATFORM_PLAN.md](CLIENT_USABLE_SWIFT_PLATFORM_PLAN.md)  
Coverage: [MESSAGE_COVERAGE_REPORT.md](MESSAGE_COVERAGE_REPORT.md)

> No SWIFT certification, complete ISO 15022 conformance, market/client acceptance, live SWIFT
> connectivity, or production readiness is claimed. Every target message remains `PARTIAL`.

## 1. Executive summary

The platform now has a secure, source-bounded authoring and operations layer over the existing
deterministic Category 5 engines. Authenticated tenant users can create empty encrypted drafts,
enter actual business values for any of the 200 configured rows, manage configured optional fields
and repeatable sequences, compose deterministic Block 4, inspect separated validation levels,
load explicit annotated synthetic samples, round-trip supported FIN, download evidence, request
review, obtain independent approval, import external validation evidence, and exercise a mock-UAT
submission lifecycle. These are engineering foundations, not a production deployment.

## 2. Starting repository state

The repository had no commits and all existing work was uncommitted, so no destructive Git action
was taken. It already contained MT530/537/540–548/564–568 configured subsets, five shared settlement
composers, workflow composers, Tag Intelligence, OpenRouter structured interpretation/cache,
SQLite/Alembic, Next.js, Excel/ZIP, Docker, 233 backend tests, and 10 Playwright tests. It had no
machine-readable specification registry, real-data authoring boundary, authentication, tenancy,
field encryption, approval, connector, external validation, or PostgreSQL driver.

## 3. Source inventory

Repository knowledge uses concise derived records and stable source references. Public primary
inventory reviewed: SWIFT Standards releases, SWIFT Standards, MyStandards, official settlement and
corporate-action training pages, and public Category 5 message-reference/usage PDFs already cited in
the plan. No current licensed SR2026 format-validation rules, MyStandards client pack, SMPG pack, or
institution guide was present. Consequently authoritative completeness is unknown and the compiler
forces `EXTERNAL_VALIDATION_REQUIRED`/`PARTIAL`.

## 4. Supported messages

Source-bounded authoring is available for MT530, MT537, MT540–MT548, and MT564–MT568. MT535,
MT536, MT538, and MT578 are read-only `CATALOGUE_ONLY`. Existing golden business lifecycles remain,
including MT541 → MT548 → MT545. Capability discovery never presents a catalogue-only message as
generatable.

## 5. Coverage per message

The registry compiles exactly 200 configured rows: MT530 5; MT537 23; MT540 14; MT541 15; MT542
14; MT543 15; MT544 12; MT545 13; MT546 12; MT547 13; MT548 12; MT564 14; MT565 10; MT566 13;
MT567 9; MT568 6. Knowledge/form/composer/parser/configured-validator coverage is 100% of that
configured denominator for every message. It is not a percentage of the unavailable official
denominator. The production gate passes for zero messages.

## 6. Tag Intelligence coverage

Every configured field has a message/sequence-specific knowledge ID, business/technical meaning,
why-used text, business question, presence/condition, format, options/codes, related fields, release,
profile overlay, and provenance. Startup rejects duplicate rows, broken sequences/dependencies,
unknown options, malformed sources, and missing target specifications. PSET remains contextual by
message and sequence rather than a generic reused definition.

## 7. Sample-message coverage

All 16 target types have a runtime sample generated by the same deterministic production composer.
Sample/golden row coverage ranges from 58.33% (MT548 golden scenario) to 100%; the exact per-message
table is in `MESSAGE_COVERAGE_REPORT.md`. Each line maps to sequence occurrence, row, tag/qualifier,
value, meaning, reason, and presence. Loaded fields remain `SAMPLE_DATA` and unconfirmed.

## 8. Real-data input

The secure builder starts empty. User values are never replaced with samples/defaults, and every
stored field carries `USER_ENTERED`, `PROFILE_DEFAULT`, `SYSTEM_DERIVED`, `IMPORTED_EXCEL`,
`IMPORTED_API`, or `SAMPLE_DATA`. Actual values are accepted for the configured rows and encrypted
server-side. Profile changes increment the revision and invalidate prior validation/approval.

## 9. MT537 implementation

The generic builder supports actual values and configured repeatable D/D1/D1a/D1a1 occurrences for
all 23 configured MT537 rows. Existing typed penalty generation supports supplied actions/statuses,
SEFP/LMFP, currencies, direction, amounts, dates, references, duplicate checks, and correlation.
Amounts are never calculated by the LLM or an unapproved formula. This is not a complete MT537
Statement of Pending Transactions specification.

## 10. Corporate-action implementation

MT564–MT568 configured rows accept actual values through the generic builder and round-trip parser.
The typed lifecycle remains DVOP-only and validates event/reference/option/quantity/deadline/status/
cash/narrative correlation. Other event profiles (DVCA, INTR, REDM, TEND, EXOF, RHTS, DVSE, MRGR)
are catalogue-only because authorised rule packs are absent.

## 11. Settlement implementation

Existing MT540–MT548 deterministic generation, negative testing, profiles, parsing, Excel, reports,
and lifecycle correlation remain green. Generic authoring adds configured optional rows, sequence
instances, actual values, provenance, immutable revisions, downloads, and operations without
replacing the five shared composers.

## 12. MT530 implementation

MT530 remains a five-row processing-command subset. The deterministic amendment engine prevents
core trade/event data from being modified through MT530 and chooses cancel/rebook or unsupported
outcomes according to configured rules. No universal amendment claim is made.

## 13. FIN envelope

The authoring service separates Block 4 from a configured FIN application envelope. Sender LT,
receiver, session and sequence are explicit inputs; interface/network-generated authentication,
trailers, ACK/NAK and checksums are never invented. Priority/MUR are bounded and validated.

## 14. Download formats

Operational: Block 4, `.fin`/`.txt`, full configured FIN, canonical JSON, validation JSON,
validation HTML, and ZIP evidence. Filenames/checksums are deterministic and path-safe. Validation
PDF is not implemented.

## 15. RJE

RJE single/batch capability models exist but export deliberately fails closed. The repository has
no approved client RJE interchange contract, so acceptance criteria 21–22 are not met and no
format was guessed.

## 16. Authentication

Server-side sessions, expiry, HMAC-protected opaque IDs, secure-cookie production enforcement,
CSRF, active-user checks, and role dependencies are implemented. The development identity adapter
is explicit and forbidden in production. OIDC/SAML protocols are defined, but no production IdP
adapter/credentials exist; production authentication is incomplete.

## 17. Tenancy

Tenants scope users, drafts, connectors, external evidence, submissions, audit events, encryption
AAD, and AI cache partitions. Cross-tenant draft/connector lookups return not-found. PostgreSQL RLS
is not configured and remains a hardening gap.

## 18. Encryption

Draft values and immutable snapshots use AES-256-GCM envelope encryption with a fresh data key and
tenant/draft/field authenticated context. Production requires an injected key and PostgreSQL.
KMS/HSM key wrapping, automated rewrap/rotation, encrypted object storage, and authorised purge are
not complete.

## 19. Review and approval

Local validation creates a checksum/version; the author requests review; another user with
`APPROVER` binds approval to revision/checksum. Self-approval is forbidden. Any sequence, field, or
profile change increments revision, resets checksum/validation, and deactivates approval.

## 20. Connectors

The registry exposes download, UAT, file, MQ, Alliance, Lite2, and custom capability types without
pretending their adapters exist. Download-only is operational. Mock UAT is explicit dev/test-only,
makes no external call, and creates clearly `MOCK` evidence. No live client connector is present.

## 21. Submission lifecycle

The implemented gated path covers DRAFT → VALIDATED → REVIEW_REQUESTED → APPROVED → mock QUEUED/
SUBMITTED/ACKNOWLEDGED evidence. It checks role, tenant, checksum, revision, approval, connector,
environment, external-evidence policy, idempotency, and dual production flags. Arbitrary destinations
are impossible. Retry/real ACK/NAK behavior awaits a contracted adapter.

## 22. External validation

Provider-neutral interfaces and uploaded evidence correlation are implemented. Evidence must match
message checksum, profile, release, status, and timestamp. There is no MyStandards/vendor/Alliance
API implementation and no target message has `EXTERNAL_VALIDATION_PASSED` based on authorised live
evidence.

## 23. LLM privacy

Deterministic forms, specifications, Tag Intelligence, samples, composition, validation, downloads,
approval and submission make no model call. OpenRouter sees only minimal tokenised intent; accounts,
references, raw FIN, full lifecycle and full canonical objects are excluded. Output cannot compose,
validate, approve or submit.

## 24. Cache behaviour

Exact HMAC cache keys include tenant partition, profile/release, workflow, prompt/schema/knowledge/
taxonomy/model versions. Current-request placeholders are revalidated and rehydrated. Failures and
unvalidated output are not cached; cache hits still pass schema and deterministic rules. L1 and
single-flight are process-local.

## 25. API changes

Added specification/catalogue/coverage/event-profile/sample endpoints; development session routes;
draft create/get/profile-patch; field/sequence add/delete; compose/validate/review/approve/submit;
downloads/audit/submissions; raw import; connector list/health/test; and external-evidence import/
retrieval. Existing APIs remain compatible.

## 26. Database migrations

review/approval, connector/submission/attempt, external-validation and audit tables. It applied from
empty SQLite and empty PostgreSQL 17 through all six migrations. No destructive migration ran.

## 30. Security

RBAC, tenant checks, CSRF, expiry, maker-checker, AES-GCM, server-side secrets, fail-closed production
settings, connector allowlists, idempotency, formula/path/FIN-fragment rejection, content-free logs,
LLM tokenisation/cache isolation, dependency audit and bundle secret scan passed. No credential or
raw financial value was printed. A formal pentest, KMS, SIEM/DLP, IdP, RLS, backup/restore and purge
workflow remain required.

## 31. Known limitations

Authoritative full-release rules are absent; all messages remain partial. RJE/PDF/nested secure
bulk templates, complete MT537 pending statements, additional CA events, OIDC/SAML implementation,
KMS/purge, live connector retries/ACK/NAK, and external validator APIs are incomplete. The test
client emits one upstream deprecation warning. The secure generic builder is sequence-oriented;
complete business-question forms and visual raw diff/unsupported-field editing for every target
message are not complete.

## 32. Unsupported capabilities

No SWIFT network transmission/certification, arbitrary field/tag authoring, arbitrary connector
destinations, live Alliance/Lite2/MQ/SFTP/HTTPS adapter, complete Category 5 catalogue, ISO 20022,
production identity federation, official penalty calculation, unverified event/code generation, or
semantic financial cache.

## 33. Production-readiness gaps

Import and approve current licensed message/rule packs; reconcile the authoritative denominator;
implement institution OIDC/SAML, KMS, PostgreSQL HA/RLS/backups, immutable/SIEM audit, retention
purge, accessibility/pentest; contract and certify connector/validation adapters; implement approved
RJE/client payload; run client UAT/external validation and operational resilience/load testing.

## 36. Final status

The configured subsets are usable for secure controlled authoring, deterministic local engineering,
evidence download, maker-checker, and mock-UAT automation. They are **not production-capable**.
Acceptance criteria related to actual values/configured optional/repeatable rows, samples, local
composition/validation, authentication foundations, tenancy, encryption, approval, mock UAT,
tests/build/migrations/Docker/audits are met. RJE, complete authoritative coverage, production IdP,
live connector, real ACK/NAK/retries, PDF, purge/KMS, nested real-data bulk, and external validation
against an authorised service are transparently not completed.
