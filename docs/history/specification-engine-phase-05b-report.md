## 1. Executive summary

Two authorised SWIFT MyStandards MT Message Reference Guides — MT540 *Receive Free* and
MT541 *Receive Against Payment*, both **Standards MT November 2026** — were read into this
repository as evidence.

Reading them is deterministic end to end. No model was called at any point: the guides state
their own structure in headings and tables, and every rule was found, placed and translated
by code that produces the same answer from the same bytes. **38 Network Validated Rules were
discovered — 18 in MT540, 20 in MT541 — and every one was recognised.** 15 translated
exactly, 15 more weakly than the source states them (with the dropped clause recorded), and
8 were refused as not soundly expressible. 30 candidate rules compiled through the ordinary
Rule Pack compiler and 24 behavioural proofs passed against synthetic values.

Every candidate is `REVIEW_REQUIRED`. None is installed. **Runtime activations: 0.** SR2026
is future-test until 14 November 2026, and MT540 and MT541 generate today exactly as they
did before — byte for byte, checksum for checksum.

The documents themselves never entered Git. What is committed is derived metadata:
identifiers, digests, page numbers, structure tables and the expressions this repository
generated. That is what lets `make check` verify the whole pipeline on a machine that has
never held a licensed document — including CI, which never will.

qualifier tables — a first-party SWIFT statement, and for this purpose a stronger source
than Prowide.

## 17. PDF extraction quality

Both text layers are clean. Page numbering, headings, tables, rule numbering and SWIFT field
syntax all survived. No OCR was used or needed. Two extraction artefacts were found and
handled rather than absorbed:

- **Row numbers alone on a line.** A wrapped Format Specification row leaves its `No.` value
  alone, indistinguishable from a page footer. Matching the page's *own* number, and only at
  the bottom of that page, fixed a silent loss of table rows (92/93 rows now parse with zero
  unparsed text).
- **Hyphenation across line ends inside SWIFT tokens.** `:22F::DB-` / `NM//VEND` is one
  field reference. Rejoining every hyphenated break repairs the tokens rules are about, at
  the cost of closing up the few genuine hyphens on a line end — a trade recorded in the
  code, and one no reviewer decision rests on.

## 26–27. Rule DSL compatibility, and the rules it cannot express

Eight rules across the two books cannot be expressed soundly. All eight are recorded with

| Message | Rule | Error | Reason |
|---|---|---|---|
| MT540 | C8 | E52 | `OCCURRENCE_SCOPE_NOT_EXPRESSIBLE` — PSET forbids 97a *in the same E1 occurrence* |
| MT540 | C14 | E63 | same — EXCH/TRRE forbid 97a in the same F occurrence |
| MT540 | C16 | E99 | same — "in each occurrence of" a repeating subsequence |
| MT540 | C17 | E88 | same — option-L ALTE excludes MEOR/MERE in the same occurrence |
| MT541 | C9 | E52 | same as MT540 C8, under MT541's own number |
| MT541 | C16 | E63 | same as MT540 C14 |
| MT541 | C18 | E99 | same as MT540 C16 |
| MT541 | C19 | E88 | same as MT540 C17 |

A presence-only version of any of these is **stronger** than the source and would reject
messages SWIFT accepts. **No DSL operator was added.** Occurrence-aware values would change
the value model of the live runtime — composer, both parsers, the MX path and the
evaluator's core type — for the benefit of candidates active nowhere. This is recorded as
the single highest-value DSL gap for a later phase.

The 15 `PARTIAL` rules are strictly *weaker* than their sources and each carries the clause
it dropped: a distinct-occurrence requirement, a data-source-scheme caveat, a format-option
constraint, or a quantity-code pairing.

## 28–31. Extraction A, extraction B, candidate diff, refuter

**`REAL_SOURCE_LIVE_LLM_EXTRACTION = BLOCKED_BY_SOURCE_POLICY`.**

The guides' licence does not establish that their text may be sent to an external model
provider, so `sourceAllowsExternalModelProcessing` and
`providerApprovedForSourceClassification` are both false and the Phase 5A extraction path
refuses. There is therefore **no extraction A, no extraction B, no model refuter, no prompt,
no cache entry, no token count and no cost** — nothing was sent anywhere.

Translation is deterministic instead: a closed set of the sentence forms the guide actually
uses, and a refusal for anything else.

**Refutation is deterministic too, and comes from the document.** Every qualifier table
carries a `CR` column naming the Network Validated Rules that govern that qualifier.
Comparing that column against what a translation binds is a criticism the source supplies —
with no way for two readings to agree by having made the same mistake. It produced **7
objections for MT540 and 6 for MT541**, all recorded on the candidates and in the reviewer
packages. Three findings are worth naming:

- The guide does **not** cross-reference its own settlement-transaction rule from the `SETR`
  qualifier row in MT541, though it does in MT540 — an asymmetry in the source itself.
- Neither guide cross-references the network-fee exclusion from `E4:36D::NTWK`, though the
  rule constrains it.
- The linked-quantity rule names `:36B:` without a qualifier; the qualifier table shows the
  sequence declares exactly `PAIR` and `TURN`, which is narrower than a bare tag reference
  and is exactly the sort of over-reach the check exists to surface.

## 32–33. Canonical reference resolution and SRU compatibility

Every reference on every recognised rule resolved against the structure the same guide
states. A reference is placed by the sequence the rule names; where it names none, the
qualifier tables decide and **only when they decide uniquely** — 14 of ~210 (tag, qualifier)
pairs are ambiguous across sequences and are reported rather than assigned to the likelier
one.

Format options are honoured: `:95L::ALTE` means option L and `:95a::ALTE` means the field
whatever option it carries. Collapsing them would silently widen the rule.

## 42. SETR findings

The guide independently confirms this repository's earlier correction, and extends it:

- `22F::SETR` sits in **Sequence E**, is **Mandatory**, order 2, option F — as configured.
- The SR2026 code list carries **42 codes** under error `K22`. This repository's
  `SETTLEMENT_TRANSACTION_TYPE` list carries **11**, all 11 of which are in the SR2026 list.
- The repository list omits `PAIR`, which SR2026 `C13` (MT541) / `C12` (MT540) requires as
  one of two permitted values. A candidate for that rule therefore names a code the current
  runtime list does not offer — recorded, not silently added.
- The list remains a documented subset. Nothing here changes it.

## 43. ISIN / 35B findings

- `35B Identification of the Financial Instrument` is **Mandatory in mandatory Sequence B**
  in both guides, format `[ISIN1!e12!c][4*35x]`, exactly one row per message. Asserted by a
  test against the evidence fixture.
- The guides state the **field syntax**. They do not state an ISO 6166 check-digit
  requirement, which confirms this repository's separation: field format is a `FORMAT`
  concern, identifier quality is a `CLIENT_PROFILE` concern with its own rule id. Nothing in
  this phase attributes the check digit to SWIFT.

## 44. Party-chain findings

- `95a::DEAG`, `PSET`, `REAG`, `SELL`, `BUYR`, `RECU`, `DECU`, `REI1`, `REI2`, `DEI1`,
  `DEI2` are all declared in **subsequence E1** and nowhere else, in both guides. Asserted
  by a test.
- `PSET` allows options `C, D, P, Q` in SR2026 — notably **not** `R`, which the installed
  subset offers as `MT541-E-95R-PSET`. Recorded as a difference for a reviewer; the runtime
  is untouched.
- The deliverer and receiver chains (`DEI2→DEI1→DECU→SELL`, `REI2→REI1→RECU→BUYR`) were
  extracted as six implications per message and are `PARTIAL`: the source requires the next
  party in *another* occurrence, and distinctness is not expressible.
- No MT540/MT541 evidence was generalised to MT542, MT543 or any other message.

## 45. Settlement-amount findings

The most consequential finding, and the one the brief specifically warned against getting
wrong in either direction:

- **MT541 requires a settlement amount.** `C2`, error `E92`: one occurrence of `E3` must
  contain `:19A::SETT`. Translated `EXACT`, compiled, and proved both ways.
- **MT540 states no such rule.** There is no `MANDATORY_QUALIFIED_FIELD` translation
  anywhere in the MT540 book, and a test asserts it.
- **MT540 nonetheless permits the amount.** Its own `C1` lists `:19A::SETT` among the
  amounts it constrains — so "receive free" means *not required*, not *not allowed*.
- **MT540 additionally lists `:19A::BOOK`, which MT541 does not.** 28 amount qualifiers
  against 27. That is the additional, genuine, source-established MT540-specific difference
  the brief asked for, and it is proved by a behavioural case.

## 60. Known limitations

Full list in [../limitations.md](../limitations.md). The ones that matter here:

- Eight rules are not expressible; five of those are the occurrence-scope gap.
- Fifteen rules are weaker than their sources, each with the dropped clause recorded.
- A field *component* — a data source scheme, a format option — cannot be referenced.
- No independent SR2026 structural source exists to cross-check the guides against.
- Translation recognises a closed set of sentence forms. Both books were fully recognised;
  another message need not be.
- Most candidates target `E1`, `E3` and `A1`, which the installed subset does not model.
- Reading a PDF needs `pypdf`, which is deliberately not a dependency.

## 64. What Phase 5B does not prove

- Not that MT540 or MT541 is SWIFT certified. No certification exists here.
- Not that full SWIFT validation is implemented. No SR2026 rule is active anywhere.
- Not that all SR2026 rules are supported. Eight are explicitly not.
- Not that SR2026 is current-live. It becomes live on 14 November 2026.
- Not that client market practice or MyStandards usage guidelines are covered.
- Not that any candidate has been reviewed by a person. None has.

3. The runtime MT structure gains `E1`, `E3` and `A1` so the rules have targets.
4. On 14 November 2026 the release lane moves, deliberately, in a commit.
